## 总结

本次审查发现多项高风险问题，其中至少以下几条可以直接造成“显控断开后不能自动恢复，必须重启程序或重新上电”的现象：

1. 普通 `send()` 没有屏蔽 `SIGPIPE`，对端断开时进程可能被 Linux 直接终止。
2. TCP 发送线程发现发送失败后没有执行 `error_process()`，`netStatus` 可能仍保持为 1，接收线程继续阻塞在旧连接上，主循环不会重新 `accept()`。
3. `recv()` 多处把 TCP 当成有消息边界的协议使用，未处理半包、粘包和 EOF；解析一旦错位，后续可能永久等待错误长度。
4. `mems_update()`、`zynq_update()`、EEPROM 回复路径存在未解锁返回；此外 `<<BR` 路径存在无条件重复解锁。一次异常命令即可使发送线程或控制线程永久卡死。
5. 发送线程在一个大包上持有 `mut`，没有发送超时；显控不读数据或链路异常时可能长期阻塞，其他控制命令无法回复。
6. 参数包 CRC 接收明确存在栈越界：变量只有 2 字节，却按 4 字节接收。

“IP 有时 ping 不通”不能仅由当前用户态源码最终定论，因为源码中没有设备树、网卡驱动、IP 配置脚本、内核日志和 PHY 状态。需要现场确认是 ARM 进程退出/卡死，还是 Linux 网卡、PHY、交换机链路或 CPU/内存压力异常。但当前代码中的死锁、进程崩溃、FD 泄漏、持续日志输出和阻塞发送，足以使设备表现为不可用，必须优先修复和取证。

## 关于非法地址、吐核和 PL 挂死的判断

你的怀疑是合理的，而且源码中确实存在可能触发用户态崩溃或错误访问 PL/UIO 映射的路径。但三种现象需要区分：

| 现象 | 更可能的层次 | 判断依据 |
|---|---|---|
| `app` 进程退出，IP 仍能 ping 通 | 用户态非法访问、SIGPIPE、栈破坏、未捕获异常 | 当前代码存在栈越界、长度越界和 SIGPIPE 风险；普通用户态进程退出通常不会让 Linux 网卡同时失去 ICMP。 |
| `app` 还在，IP 能 ping 通，但 7000 端口连不上 | 用户态死锁、阻塞发送/接收、连接状态机卡死 | 当前 `mut` 有永久锁死路径，发送线程可能长时间阻塞，`netStatus` 可能停留在 1 而不重新 `accept()`。 |
| IP 也 ping 不通，整机需要上电恢复 | 内核/网卡/PHY/PL 总线/DDR/电源或 CPU 饥饿 | 单纯的用户态 `SIGSEGV` 一般不会让 ICMP 消失；若同时 ping 失败，应重点看 kernel oops、外部 abort、AXI/DDR 错误、网卡 link、IRQ storm、看门狗和硬件复位。 |

源码中与非法地址/PL 访问直接相关的重点如下：

- `src/upper_to_fpga.c:258` 的 4 字节写入 2 字节变量是明确的栈越界。
- `src/upper_to_fpga.c:630-651` 的 `sersor_lenth` 来自网络，却可超过 100 字节，能直接覆盖栈。
- `src/upper_to_fpga.c:1032-1047` 的 `sprintf()` 可能溢出 `file_size[5]`。
- `src/fpga_to_upper.c:292-299` 写越界 `temp_data` 1 字节。
- `src/CuBeamOne.c:204-218` 的 `my_copy()` 会按 64 字节向上取整，可能访问数据有效区之外。
- `src/upper_to_fpga.c:236-237,303-305` 用由显控参数计算出的 `dac_sn * 4` 直接写 TVG UIO 映射，没有上限校验；坏参数可能写穿映射区或使 PL 收到非法配置。
- `src/fpga_init.c:67-79` 在 `open()` 或 `mmap()` 失败后只打印错误，不中止初始化；后续仍会把失败的映射当作有效地址使用。
- `src/upper_to_fpga.c:318-321` 对 DDR head 映射固定 `memset(..., 20000)`，没有确认 map size 至少为 20000 字节。
- `src/fpga_init.c:121` 的 `int * + 0x100` 实际是 0x400 字节偏移，可能读取错误的 FPGA 状态地址。
- UIO 允许用户态直接读写 PL 寄存器；未校验范围、未使用明确的 `volatile`/内存屏障、未确认缓存属性时，可能出现参数未生效、读到旧状态、IRQ 异常或 PL 状态机不一致。

因此，当前最符合源码证据的优先假设是：一次参数/协议异常先破坏用户态栈或触发 SIGPIPE，或者先造成 mutex/发送状态卡死；如果现场同时出现 ping 丢失，则再怀疑 PL/AXI/DDR/网卡或系统级故障，不能只用“app 崩溃”解释。

## 区分 app 崩溃、用户态卡死和 PL/系统挂死

现场复现时应先记录，不要立即重启：

1. `ps` 查看 `app` 是否仍存在；存在但端口不通，优先检查线程栈和 futex/`send`/`recv` 阻塞。
2. `ss -lntp` 查看 7000 端口和连接状态；若监听 socket 消失，检查进程退出或 bind/重启失败。
3. `dmesg -T` 查看 `segfault`、`SIGBUS`、`external abort`、`Unhandled fault`、`Kernel panic`、`oom-kill`、网卡 link 和 AXI/DDR 错误。
4. 查看 `/proc/interrupts`：若 UIO/网卡中断计数暴涨，可能是 PL 或网卡 IRQ storm；若完全不增长，可能是 PL 没有产生中断或设备已挂死。
5. 查看 `ip -s link` 和 PHY/link 状态：如果 RX/TX error、carrier、丢包随故障变化，重点转向网卡/PHY/交换机。
6. 若怀疑吐核，在启动脚本或调试环境中启用 `ulimit -c unlimited`，保存与当前 `src/app` 完全匹配的带 `-g` 符号程序；用目标架构 GDB 执行 `gdb ./app core`，先取 `bt full`、`info threads`、`thread apply all bt full`、`info registers`。若是 `SIGBUS`，重点查看 fault address 和当前是否在 UIO/MMIO 访问指令。

建议额外增加 watchdog/心跳和错误计数：主线程、TCP 收发线程、UIO 中断线程分别更新时间戳；检测到发送/接收超过阈值或 mutex 长时间未释放时输出线程状态和连接代次。这样可以在下一次故障时判断是“进程死了”“线程锁死”还是“PL/内核不再调度”。

## 与“长时间断开、IP 间歇性 ping 不通”最相关的故障链

### 链路一：显控关闭或网络瞬断

1. 数据线程或状态线程继续 `send()`；普通发送未屏蔽 SIGPIPE，进程可能直接退出。
2. 如果先由发送环形队列发现错误，`tcp_tx_ring.c` 没有调用 `error_process()`，`netStatus` 不清零，接收线程还在旧 fd 上运行，不会重新 `accept()`。
3. 如果显控只是停止读而不是立即复位连接，阻塞发送会占住 `mut`；状态、参数和 EEPROM 命令均无法取得发送锁。
4. 如果此前发生 MEMS/ZYNQ/EEPROM 异常返回，`mut` 可能已经永久锁住；表面上看就是设备在线但不再响应，重启后恢复。

### 链路二：TCP 半包导致协议错位

TCP 只提供字节流。当前代码先收 2 字节、再收 2 字节、再收固定长度，但没有保证每次收满；一次只收到 1 字节就会丢失边界。之后某个数据字节会被解释为长度，接收线程可能等待很大的错误长度，显控认为设备断开。

### 链路三：IP 真正不可达

当前源码没有网卡驱动、设备树、IP 配置、PHY 复位或链路监控实现，所以不能证明 IP 不通是由用户态程序造成。现场必须区分：

- 进程已退出：优先看 SIGPIPE、栈越界、非法 UIO/MMIO、参数越界。
- 进程仍在但 7000 端口不通：看 `netStatus`、线程栈、互斥锁、socket 状态和 fd 数量。
- 进程仍在且端口存在，但 ICMP 也不通：看 `dmesg`、网卡统计、PHY/link、`/proc/interrupts`、CPU/内存压力和交换机端口。

## 建议的修复顺序

1. 先处理 NET-01/02/03/04/05/06/07/08：修复越界、统一 SIGPIPE/发送错误处理，并消除所有手工解锁路径。
2. 用一个 TCP 会话管理器统一负责 `accept`、连接状态、断线关闭和重连；只允许一个发送线程写 `Connect_fd`。
3. 实现严格的 `recv_exact()` 与应用层解析状态机，给每个长度字段设置上限和超时；不要直接把网络字节流 memcpy 到结构体。
4. 按协议重新生成 wire format，明确 CRC 是 2 字节还是 4 字节、字段 offset、字节序和 float 表示；实现发送 CRC。
5. 修复参数长度、MEMS、温度、`my_copy` 和 UIO/MMIO 问题，删掉逐帧高频日志。
6. 增加运行指标：断线原因/errno、连接代次、发送队列深度、丢帧数、socket fd 数、线程心跳、UIO 中断速率和内存使用。

## 现场复现与取证建议

复现时不要先重启，先保存以下信息：

```sh
ps -o pid,stat,etimes,rss,vsz,cmd -C app
ss -lntp
ls /proc/$(pidof app)/fd | wc -l
cat /proc/interrupts
ip -s link
dmesg -T | tail -n 200
```

如果进程仍在，可用 `strace -ff -tt -p <pid> -e trace=network,read,write,close,futex` 观察是否卡在 `send`、`recv` 或 `futex`。如果进程消失，优先查看退出码、内核日志和是否出现 SIGPIPE/segmentation fault；如果进程和 7000 端口都正常但 IP 仍 ping 不通，则应把排查重点转向网卡/PHY/设备树/内核，而不是继续只改 TCP 业务代码。

## 审查限制

本次是基于给定源码和协议文档的静态审查，未执行 Zynq7020 实机、未获取设备树/网卡配置/内核日志，也未能使用 Makefile 中写死的交叉编译器进行目标架构编译。因此，报告中标为“明确”的内存越界、锁路径和协议长度问题可直接由源码确认；UIO 实际地址、缓存属性、PHY 故障和 ping 丢失的最终根因仍需结合实机证据确认。
